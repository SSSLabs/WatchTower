# WatchTower 项目计划书

> 版本：v0.2（评审修订稿）　代号：WatchTower（瞭望塔）
> 阶段顺序：先态势感知，后 C2　技术路线：TypeScript 全栈，不用 Rust（重仿真计算除外，见第 9.4 节）

WatchTower 是一个基于地图的态势感知系统，后期扩展为指挥与控制（C2）系统。第一阶段只做一件事：把多源数据融合成一份所有人一致的态势图（COP），做到看清、看懂、能预测。地图是底座和呈现界面，不是系统全部；核心在地图之上的融合、航迹、识别和评估。

## 1 项目定位

### 1.1 一句话定位

在浏览器里运行的、以地图为统一空间基准的无人机态势感知系统：多源观测进来，融合出连续航迹和事件告警，所有界面看到同一份态势，并能对近未来做轨迹与冲突预测。

### 1.2 目标与成功标准【建议】

- 目标：用模拟数据跑通“多源观测 → 融合航迹 → 识别评估 → 预测告警 → 统一呈现”的完整链路，并验证 COP 的一致性、可回放性和实时性能。
- 使用者：单人操作员（开发者本人或演示观众），不考虑多席位。
- 成功标准：① 第 7.7 节验收通过；② 第 12.1 节性能指标达标；③ 任意想定在同一种子下可完全复现。
- 项目用途（学习验证 / 作品展示 / 产品原型）见 D4，它决定界面打磨与文档投入的深度。

### 1.3 阶段顺序（已确认）

1. **第一阶段：态势感知。** 看清、看懂、预测，不下命令。
2. **第二阶段：C2。** COP 稳定之后，再加决策、命令下发与执行跟踪。

顺序不能倒置：没有稳定的 COP，C2 没有可指挥的对象；同时做两层，会把融合问题和决策问题搅在一起。

### 1.4 第一版边界

- 数据全部为模拟，不接真实设备，不处理真实敏感数据。
- 单人使用，不做登录与权限。
- 2D 地图为主；3D 地形按第 6 章第一档预留，不作为验收项。
- 不做服务端渲染（SSR）、搜索引擎优化（SEO）和多页面站点。
- 不做 C2 操作（返航、盘旋、终止等），见第 7.6 节。
- 桌面浏览器优先；窄屏只保证布局不崩，不作为验收项。【建议】

### 1.5 运行环境【建议】

桌面版 Chrome / Edge / Firefox 近两个主版本，要求 WebGL2。性能指标的基准机器见 D4。

## 2 参考项目与设计原则

Sokoly（无人机态势模拟指挥台）与 Simulate（开源飞行模拟器）均为 luofang34 的开源项目，形态为 Rust + WebAssembly + 静态托管。WatchTower 借鉴它们的分层思路和想定组织方式，不照搬 Rust + egui + 单 canvas 的实现，也不复用其代码；如需复用想定或素材，先核对许可证（D2）。

- 保留：地图与业务解耦、想定文件驱动场景、模拟时钟、实体 / 航迹 / 事件分开建模。
- 不照搬：Rust 地图栈。maplibre-rs 为实验性项目，Walkers 仅 2D 栅格，Galileo 仍在开发中，版本兼容性需反复核实；JS 地图生态成熟得多。
- 区分：Simulate 是飞行模拟器，地图只是它的底图；其 3D 视景与重仿真计算不属于地图层。

**设计启示**：Simulate 的导航对比实验显示，纯惯导 + 气压高度飞行约 2 分 25 秒即漂移约 654 m，带 GNSS 或视觉地形匹配的组合可收敛到米级（数据来自参考项目页面，未独立核实）。同一目标在不同来源下位置可差几百米，因此融合层必须处理来源间的不一致，位置必须带不确定性，不能直接取最后一个值。

## 3 概念体系：态势感知、C2、C3、C4

C2 = Command（指挥）+ Control（控制）；C3 加 Communication（通信）；C4 再加 Computer（计算机）。能力大致层层叠加：态势感知 → C2 → C3 → C4。地图是各层共用的底座，往上每层增加的都是地图之外的东西。

| 层级 | 主要功能 | 结构特征 |
| --- | --- | --- |
| 态势感知（第一阶段） | 多源接入与归一化；融合关联与航迹管理；识别分类；关系与威胁评估；轨迹与冲突预测；输出 COP 与告警 | 接入适配器；融合引擎（Worker）；单一状态 Store；地图 / 列表 / 详情 / 告警同源呈现；显式态势时间 |
| C2（第二阶段） | 决策队列、任务分配、命令下发、执行跟踪、审计 | 决策层与命令通道；命令校验权限与归属；每条命令有状态机与回执 |
| C3 / C4 | 多节点可靠通信；计算基础设施 | 不在本计划范围，仅说明位置 |

## 4 总体架构

系统分四层，下层只向上提供能力，不反向依赖业务：

```text
C2 层（后期）        决策队列 · 命令下发 · 执行跟踪 · 审计
态势感知层           融合关联 · 航迹滤波 · 识别分类 · 关系评估 · 预测 · COP
地图呈现层           底图 · 地形 · 业务叠加层 · 相机与交互
数据层               瓦片与样式 · 想定文件 · 模拟观测流 ·（后期）后端 API
```

### 4.1 全局约束

- **单一数据源。** 所有实体、航迹、事件只有一份权威状态。地图、实体列表、详情面板、告警栏都从同一个 Store 读取，禁止各界面各自维护状态。
- **权威状态在引擎侧。**【建议】融合与评估运行在 Web Worker，其内部状态是 COP 的唯一权威副本；主线程 Store 是它的只读快照，按固定频率同步。界面只读快照，不反向修改。
- **核心引擎与界面解耦。**【建议】仿真、融合、评估、预测写成不依赖 DOM、React 和地图库的纯 TypeScript 模块，可在 Node 中无头运行，用于自动化测试与批量验证。
- **融合与渲染分离。** 计算在 Worker，主线程只负责渲染。
- **实体不走 React 逐个渲染。** 高频位置更新走地图图层或 deck.gl 图层，不让每个实体触发 DOM 更新。
- **不确定性保留。** 每个位置、速度都带精度与最后更新时间；界面用变灰、虚线等方式表达过期与低置信，不假装精确。
- **地图只画 COP，不算 COP。** 地图层不做融合与评估；态势感知层不操作 DOM。
- **确定性。**【建议】同一想定 + 同一随机种子 + 同一引擎版本，输出完全一致。核心模块使用可播种的伪随机数，禁止直接使用 `Math.random` 和系统时钟。

### 4.2 时间与回放【建议】

- **态势时间**：所有计算以态势时间为准，系统墙钟只用于界面刷新。时钟按固定步长推进，倍速只改变推进速率，不改变步长。
- **观测时间**：每条观测带观测时间（传感器采到的时刻）和接收时间。引擎按观测时间处理，允许有限乱序窗口（初值 2 s），超出窗口的观测丢弃并计数。
- **回放方案**：记录想定、种子、引擎版本和原始观测流，重放时重新融合；每隔固定态势时间（初值 10 s）保存一次引擎快照，回看某一时刻 = 载入最近快照后向前推进。该设计从阶段 3 起落实，不留到阶段 5 补。
- 引擎版本变化后结果可能不同，旧记录须标注版本，不保证跨版本逐帧一致。

### 4.3 代码组织【建议】

单仓库。`src/core`（纯 TS 引擎：模型、仿真、传感器、融合、评估、预测、时钟）与 `src/app`（Vite + React 界面、地图图层、Worker 入口）分离，lint 规则禁止 core 引用 DOM、React 与地图库；想定放 `scenarios/`，文档放 `docs/`。规模变大时可拆为 workspace 包。

### 4.4 调试视图【建议】

地图可分别开关三层：仿真真值、原始观测、融合航迹，并显示误差。融合开发与验收离不开它。仅开发模式启用，不属于 COP 呈现。

### 4.5 界面布局

全屏单页：中央地图，左侧实体列表，右侧选中实体详情，下方或侧边告警与事件栏，顶部为模拟时钟与播放控制（播放、暂停、倍速、回放进度）。窄屏下左右面板收为抽屉，优先级低（见第 1.4 节）。

## 5 第一步：地图实现

地图是分层的数据、渲染与交互系统，业务实体只是叠在上面的图层。本阶段目标是选成熟库加成熟数据源把底图跑起来，不自研地图引擎。

### 5.1 数据与资源

- **矢量瓦片**（`.pbf`）：道路、建筑、水系、地名；默认底图路线。
- **栅格瓦片**（`.png`）：影像底图，按需。
- **地形瓦片**：PNG 像素存高程，供 3D 地形与高程查询。MapLibre 的 `raster-dem` 源须显式指定编码（`terrarium` 或 `mapbox`），两者解码公式不同，编码必须与数据源匹配。
- **配套资源**：样式 JSON、Sprite 图标、字体字形包（glyphs）。中文地名需要含 CJK 字形的字体包，体积较大，选型时确认。【建议】
- **数据源与署名**：数据源选择见 D5。使用 OpenStreetMap 等数据必须按许可证显示署名；公共瓦片服务另需遵守其使用条款，不可高频压测。【建议】

### 5.2 坐标约定

- 数据与引擎内部使用 WGS84 经纬度；地图显示用 Web Mercator（EPSG:3857）XYZ 瓦片，由 MapLibre 处理。
- 屏幕像素、相机坐标、Mercator 坐标、经纬度之间的换算由地图库提供；实体定位、点击选中、轨迹绘制都依赖它。
- 融合滤波不在经纬度上做，而在以想定中心为原点的局部东北天（ENU）平面坐标系中做，输出时转回经纬度。想定区域跨度很大时再另议。【建议】
- MGRS 在经纬度之上转换，只用于坐标显示与播报。

### 5.3 加载与缓存

流程：相机移动 → 算出视野内所需瓦片 → 先查缓存，未命中再请求 → 解码 → 渲染。

- 优先加载当前级别、视野中心附近的瓦片；拖动时取消不再需要的请求；失败瓦片有重试与超时，不能永久缺块。
- 缓存分层：HTTP 缓存、Service Worker、IndexedDB / OPFS，设缓存上限与过期策略。
- 离线走 PMTiles：区域打包成单个 `.pmtiles` 文件，用 HTTP Range 按需读取。时机见 D3。

### 5.4 渲染

默认矢量路线，直接用 MapLibre GL JS：缩放不模糊、可换样式、可做 3D。3D 地形用 `raster-dem` 源加 `setTerrain`，设高程夸张系数（如 1x / 2x）；低起伏地区在低夸张下近乎平坦，属正常现象。

### 5.5 叠加层与交互

实体图标、轨迹线、任务区、地理围栏是业务层画在底图之上的叠加层。渲染顺序自下而上：底图 → 地形 → 道路与标注 → 业务图层 → 界面元素（选中框、提示）。

相机是独立状态：中心经纬度、缩放级别、方位角、俯仰角，可编码进链接（URL hash）分享同一视角。

### 5.6 成熟度判断

地图约 80% 是成熟模式（坐标公式、数据格式、渲染库、公开瓦片服务），约 20% 必须按场景定制（实时高频更新、离线弱网、3D 与通视、军标与样式、数据源与安全），逐项做法见第 6 章。

### 5.7 验收

断开业务模拟，只留地图：拖动缩放不卡顿，瓦片不缺块，一个固定经纬度的标记随地图缩放正确移动且可点击选中，位置与经纬度对得上，署名显示正确。

## 6 六项定制需求在 JS 中的落地

以下六项是普通 Web 地图很少处理、态势系统必须处理的部分，在 JS 生态都有成熟做法，其中离线、符号、栈适配三项 JS 比 Rust 路线更容易。

| 定制需求 | 为什么必须定制 | JS 落地做法 | 规模边界 / 备注 |
| --- | --- | --- | --- |
| 实时性 | 态势每秒刷新，千级实体位置与轨迹同时更新，不优化会整体卡顿 | MapLibre GeoJSON Source 更新（整体 `setData`，或所用版本支持的局部更新接口）；deck.gl 实例化图层；只渲染视野内实体；缩小时用 Supercluster 聚合；融合放 Worker | 经验值：几千实体 MapLibre 足够，上万加 deck.gl。阶段 2 用基准测试验证 |
| 离线和弱网 | 野外、断网不能依赖在线瓦片 | PMTiles + MapLibre `addProtocol`；Service Worker + Cache API / IndexedDB / OPFS 预下载并设上限；断网自动降级到本地包 | 标准做法 |
| 3D 和地形 | 飞行视景、通视分析、高程夸张由场景决定；首版 2D 足够 | 第一档：`raster-dem` + `setTerrain`；第二档：真 3D 地球与通视换 CesiumJS | 首版只预留第一档。第二档会替换整个呈现层（实体、航迹、军标图层须在 Cesium 中重写），不是配置切换，启用前单独评估 |
| 符号和样式 | 军标 APP-6、MGRS 格网、暗色指挥主题、标注避让都不是默认样式 | `milsymbol` 由 SIDC 生成军标并注册为地图图标；`mgrs` 做坐标互转，格网线用自定义图层；主题改样式 JSON | 无需自绘军标库 |
| 技术栈适配 | Rust 地图栈不成熟（见第 2 章） | 全套 JS 库直接使用，无 WASM 桥接与版本钉死问题 | 桌面端 Electron / Tauri、移动端 PWA 仅作后路，不在第一版范围 |
| 数据源和安全 | 第三方瓦片能否用、有无保密要求、是否自建，是产品决策不是技术细节 | 自建 TileServer GL / Martin，或 PMTiles 自托管；瓦片地址加 token、内容安全策略（CSP）、访问审计在配置层完成 | 第一版用公开源（见 D5）；切换自建源只改配置 |

唯一明确的边界是重仿真计算（如 JSBSim 类高频物理推演）：到达那一步时，把那一小块核心抽成 Rust 编译的 WASM 模块放进 Worker，其余仍留在 JS（见第 9.4 节）。

## 7 第二步：态势感知

态势感知不是地图，地图只是它的输出界面。地图回答东西在哪，态势感知回答现在发生了什么、意味着什么、接下来会怎样。采用 Endsley 三级模型：感知、理解、预测，对应实现上的三个阶段。第一版数据为模拟，因此先要有仿真层（第 7.1 节）来产生观测。

### 7.1 仿真与观测生成【建议】

融合算法只有面对不完美的数据才有意义。若仿真直接输出精确位置，融合就是空转，验收也没有说服力。

- **真值层**：按想定推进的无人机与目标的真实状态，仅供仿真与评分使用，不进入 COP，融合与评估不得读取。
- **传感器模型**：每个模拟数据源配置更新频率、位置与速度噪声、探测范围、漏检概率、虚警（杂波）、时间延迟与抖动、时钟偏移、偶发乱序与重复、坐标系与单位差异、是否携带稳定 ID。
- **观测流**：真值经传感器模型生成观测，写入记录（第 4.2 节）。
- **评分**：用真值给 COP 打分——位置误差、航迹连续性、ID 切换次数、漏跟与误跟、虚假航迹——用于验收与回归（第 7.7 节）。
- **困难片段**：想定中刻意包含目标交叉或近距并行、短时遮挡与丢帧、双源重复报同一目标、单源时钟偏移。

### 7.2 第一级：感知（看清）

把所有来源的数据收进来，变成统一的观测。

- **数据源**：第一版为模拟想定产生的无人机遥测与目标探测；真实系统还包括雷达、ADS-B、摄像头、地面传感器、人工上报与情报。接入接口按真实源的形态设计。
- **接入与归一化**：各源的格式、坐标系、时间基准、更新频率不同，统一成同一数据模型（第 10 章）。时间必须对齐，否则两个源报同一目标会差出几百米。
- **时效**：超过设定秒数未更新的观测标记过期、变灰，最终丢弃，不让失效目标长期留在图上。

这一级的输出只是一堆带时间戳的观测，还不是实体。

### 7.3 第二级：理解（看懂）

态势感知最核心的一层，输出是 COP：所有人看到的同一份、经过融合与评估的态势。

- **多源融合与关联**：按位置、速度、航向、时间判断哪几条观测属于同一目标，接近且运动一致的合并。跟踪关系（如某无人机跟踪某地面目标）在这一层建立。
- **航迹管理与滤波**：目标不随每次观测跳动，而是形成连续航迹；滤波平滑噪声、补齐丢帧、预测下一时刻位置；航迹有生死管理。
- **识别与分类**：为实体打标签：阵营（我方 / 敌方 / 中立 / 未知）、类型（无人机、车辆、人员等）、状态（巡逻、跟踪、盘旋、返航、失联），以及电量、高度等属性。
- **关系与威胁评估**：计算距离、是否进入任务区、电量是否够返航、速度航向指向谁；规则引擎产出事件与评分：进入禁区、电量低于阈值、间距小于安全距离、目标长时间静止。

**算法基线**【建议，阶段 4 开始前复核】：

- 滤波：恒速（CV）卡尔曼滤波起步，机动明显时再升级到恒加速或交互多模型（IMM）；在局部 ENU 坐标中运行。
- 关联：有稳定 ID 的观测先按 ID 关联；无 ID 的用马氏距离门限加全局最近邻（匈牙利算法）；用网格空间索引控制千级实体的计算量。
- 航迹生命周期：暂定 → 确认 → 滑行（无观测，仅外推）→ 终结；确认用 M/N 逻辑（N 次观测中命中 M 次）；超时未更新则终结。航迹编号不复用。
- 识别：阵营与类型取自来源属性（如敌我识别字段）与分类置信度，证据不足时为“未知”，随证据累积更新。
- 评估规则：阈值由想定配置；告警带滞回与去抖，避免在阈值附近反复触发；事件有新建、已确认、已清除状态。

### 7.4 第三级：预测（预判）

- **轨迹外推**：按当前速度航向算 30 秒、1 分钟、5 分钟后的位置；不确定性范围由滤波协方差随时间增长给出。机动目标的远期外推可信度低，界面要体现。
- **冲突与到达预测**：是否进入禁区、是否相撞、何时到达目标点、电量是否够飞回。电量预测需要返航点与简化能耗模型（第 10 章）。
- **假设推演**：若改派另一架无人机跟踪某目标，需要多久、是否与现有航线冲突。只提供参考，不下命令。

### 7.5 处理流水线

```text
想定 → 仿真（真值）→ 传感器模型 → 观测流（可记录）
     → 接入适配器 → 归一化（坐标 / 时间 / 单位）→ 融合关联 → 航迹滤波
     → 识别分类 → 关系评估 → 生成 COP → 告警事件 → 预测
     → 呈现（地图 + 列表 + 详情 + 告警栏）
```

前三步属于仿真，后期接真实数据源时替换为真实接入，其后的流水线不变。实现要点见第 4.1 节。

### 7.6 与地图、与 C2 的边界

- 地图只负责把 COP 画出来，不负责计算 COP。
- 态势感知只负责看清、看懂、预测，不负责下命令。它输出的是“建议关注某目标、它正在接近任务区”；由谁去处置是 C2 的决定。
- 界面上的返航、盘旋、终止等操作属于 C2，不计入第一阶段范围。

### 7.7 验收

用模拟数据跑通整条流水线，使用两个想定：**基础想定**（3 架无人机 + 2 个地面目标）与**复杂想定**（含第 7.1 节全部困难片段，实体数更多）。每个想定都要再用非默认参数（起始时间、时长、随机种子）复验一遍；默认场景恰好不触发的问题，不算通过。

指标为建议初值，阶段 4 开始前复核：

- **航迹**：基础想定 ID 切换 0 次、无虚假航迹；复杂想定 ID 切换不超过 2 次，虚假航迹持续不超过 10 s。
- **精度**：融合位置误差（RMSE）不高于最优单源观测的误差。
- **告警**：规则触发时间与按真值算出的触发时间偏差不超过 2 s；阈值附近不反复触发；跟踪关系与电量告警正确。
- **一致性**：地图、列表、详情、告警对同一实体的描述自动对账一致。
- **回放**：同想定、同种子两次运行的 COP 逐帧一致；可暂停、可回放、可回看任意时刻，结果与当时一致。

满足即视为态势感知层立住，C2 才有可指挥的对象。

## 8 后期展望：C2

C2 在第一阶段验收通过后启动，本章只定方向与边界，不排期。

### 8.1 功能范围

- **决策队列**：态势感知产生的事件进入待决策队列，操作员逐条批准、驳回或改派。
- **任务分配**：把目标分配给具体无人机，校验航线冲突与电量可行性（复用第 7.4 节的假设推演）。
- **命令下发**：返航（RTB）、盘旋（Loiter）、终止、改航点等；每条命令有状态：已发出、已确认、执行中、已完成、失败。
- **执行跟踪**：执行情况回写到 COP，能看到谁在执行什么。
- **审计**：谁在什么时间对哪个实体下了什么命令，结果如何。依赖后端，见第 9.3 节。

### 8.2 多人与 RBAC

多人使用与角色权限（RBAC）在这一阶段才成为刚需。RBAC 是一套权限模型，不由前端框架提供：后端维护用户、角色与权限关系，登录后签发带角色的 JWT，每个接口在后端再校验一次；前端只按角色隐藏按钮、守住路由。只靠前端隐藏按钮拦不住越权。SPA 完全可以做 RBAC，不需要为此换框架。

### 9.1 前端

| 军标 / 格网 | milsymbol / mgrs | SIDC 生成 APP-6 符号 / MGRS 与经纬度互转 |

| 测试 | Vitest；Playwright（后补）【建议】 | core 单元与回归测试；端到端 |
| 规范 | ESLint + Prettier + pnpm + Node LTS【建议】 | |

应用形态为单页应用（SPA）：全屏单页指挥台，无多页面、无 SSR 需求。

### 9.2 工程与质量【建议】

- **测试**：core 单元测试；以固定想定 + 种子的 COP 输出摘要作为“黄金记录”，改动算法后做回归比对；确定性测试（同种子两次结果一致）。
- **CI**：提交即跑 lint、类型检查、测试与构建（如 GitHub Actions）。
- **部署**：静态托管。默认不使用 `SharedArrayBuffer`（它需要 COOP / COEP 响应头，GitHub Pages 无法设置）；Worker 与主线程用可转移对象（Transferable）传递二进制数据，阶段 0 做一次往返基准。
- **依赖与合规**：锁定依赖版本，地图库固定主版本；立项时核对各依赖的许可证与地图数据署名要求。
- **文档**：重大决策写入 `docs/` 决策记录，每阶段结束更新本计划书。

### 9.3 后端（后期，按需加入）

第一版纯 SPA、无后端：想定读本地 JSON，记录走文件导入导出与 IndexedDB（第 10.3 节）。后端只在需要多人登录、RBAC、持久化、审计或接真实设备时加入，加入时前端只把读本地 JSON 的地方改成调用接口，不重写。

方向（阶段 9 前再定具体选型）：TypeScript + Node.js + Fastify；Prisma；SQLite 起步，多人并发写时迁 PostgreSQL；认证用现成方案（如 Keycloak、Auth.js），不自研，自研只限 RBAC 的用户、角色、权限关系与接口校验。前后端分开部署，经 HTTPS 与 WebSocket 连接。

分工：前端只负责展示与交互；后端负责发令牌、校验权限、存数据、记审计、推实时数据、向真实设备下发命令。例如批准返航：前端只发请求，后端校验操作者角色、权限与任务归属后才执行并记日志。

### 9.4 决策记录

| 决策 | 结论 | 理由 | 重新评估条件 |
| --- | --- | --- | --- |
| 语言 | TypeScript，不用 Rust | 瓶颈在 GPU 渲染与网络，不在 CPU；Rust 地图生态弱于 JS；第一版要迭代快 | 重仿真计算成为瓶颈时，仅把该小块抽成 Rust WASM 模块放入 Worker，其余不换语言 |

| 界面框架 | 从一开始用 React，不用原生 TS | 原生状态管理在列表、筛选、决策、回放面板加入后很快失控 | — |

| 阶段顺序 | 先态势感知，后 C2 | 见第 1.3 节 | — |

## 10 数据模型

第一版用 TypeScript 类型定义，后端加入后同一套模型映射为 Prisma schema。

### 10.1 约定

- **时间**：区分墙钟时间（UTC 毫秒时间戳）与态势时间（自想定起点的毫秒偏移）；业务计算只用态势时间。观测带观测时间与接收时间（第 4.2 节）。
- **位置**：WGS84 经纬度（度）。高度必须标明基准（海拔 MSL / 离地 AGL / 椭球高 HAE），引擎内部统一为 MSL，接入时转换。【建议】
- **单位**：距离 m，速度 m/s，航向为度（真北起顺时针），电量 0–1。【建议】
- **原始值与估计值**：位置同时保留原始观测值与融合估计值，不覆盖原始数据。
- **精度与置信度分开**：位置与速度精度用标准差或协方差（m、m/s）；分类置信度为 0–1，不当作位置精度使用。【建议】
- **编号**：观测编号在来源内唯一；航迹编号系统内唯一且不复用；实体编号稳定。【建议】

### 10.2 模型

| 模型 | 核心字段 | 说明 |
| --- | --- | --- |
| 观测 Observation | 编号、来源、观测时间、接收时间、经纬度、高度及基准、速度、航向、位置精度、分类线索、置信度 | 原始输入，未经融合，不直接呈现 |
| 实体 Entity | 编号、阵营、类型、状态、电量等属性、当前航迹编号 | 融合后的对象，列表与详情展示的就是实体 |
| 航迹 Track | 实体编号、位置序列、当前估计位置与速度、协方差、最后更新时间、状态（暂定 / 确认 / 滑行 / 终结） | 连续轨迹，带生死管理 |
| 跟踪关系 Link【建议】 | 跟踪方实体、被跟踪方实体、建立时间、失效条件、状态 | 第 7.3 节建立的关系，单独建模 |
| 事件 Event | 类型、涉及实体与区域、触发规则、严重程度、发生时间、处理状态（新建 / 已确认 / 已清除） | 告警与评估的输出，后期进入 C2 决策队列 |
| 区域 Zone【建议】 | 类型（任务区 / 禁区）、几何、高度范围、生效时间 | 地理围栏，事件引用区域 |
| 想定 Scenario | 名称、区域、任务起止时间、随机种子、初始实体、返航点、区域、传感器与数据源配置、规则阈值、schema 版本 | 场景的完整定义，JSON 保存与加载，加载时校验 |
| 真值 Truth【建议】 | 仿真实体的真实状态序列 | 仅供仿真与评分，不进入 COP |
| 记录 Recording | 想定编号、种子、引擎版本、观测流、事件序列、周期快照 | 支撑暂停、回放与按时间回看 |

### 10.3 持久化（第一版）【建议】

想定为带版本号的 JSON 文件；记录以文件导出与导入为主，浏览器内用 IndexedDB 暂存。服务端存储留到阶段 9。

## 12 非功能需求与风险

### 12.1 非功能需求

- **性能**【建议初值，基准机器见 D4】：1000 个实体每秒更新时，主线程帧率不低于 30 fps（目标 60）；融合单次处理不超过 200 ms；融合不阻塞渲染线程。
- **离线**：按 D3 的结论执行；无论何时做，都要有缓存上限与断网提示，不能无限缓存或静默失败。
- **安全**：数据标注为模拟；涉及真实数据时，瓦片源、接口令牌与审计按第 6、9 章执行；不得默认第三方瓦片可用于敏感场景。
- **一致性**：任何时刻地图、列表、详情、告警对同一实体的描述必须一致，以 Store 为唯一依据对账。
- **可回放**：任何已运行的想定都能按态势时间回放，同引擎版本下与当时呈现一致（第 4.2 节）。
- **可访问性**【建议】：暗色主题下阵营区分不能只靠红绿色，须配合形状或标记。

### 12.2 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 融合只在理想数据上验证 | 验收通过，遇到噪声、丢帧、重复就失效 | 第 7.1 节传感器模型与复杂想定，评分对照真值 |
| 只验默认想定 | 非默认起始时间、时长、种子下出现溢出、乱序或崩溃，误判为已完成 | 每阶段验收强制加非默认参数复验 |
| 回放留到后期补 | 状态没按可重现设计，到阶段 5 才发现无法回放 | 第 4.2 节：阶段 3 起即做确定性与观测流记录 |
| 实体更新走 React 逐个渲染 | 千级实体时整体卡顿 | 实体走地图 / deck.gl 图层，融合放 Worker（第 4.1 节） |
| Worker 与主线程通信开销 | 高频同步拖慢主线程 | 快照按固定频率同步，用 Transferable，阶段 0 做基准 |

## 附录 B 命名备选
